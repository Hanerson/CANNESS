# CANN 算子自动化生成 Harness 项目可行性评估与实施建议

文档版本：v1.0  
编写日期：2026-08-31  
评估对象：CANN 算子自动化生成 Harness  
参考材料：`cann-harness-design-guide.md`

## 1. 执行摘要

本项目目标是构建一个面向 CANN 算子的自动化生成、转换、评测、反馈修复和知识沉淀系统。该方向具备明确的工程价值，尤其适合 CANN 算子这类可通过编译、精度和性能评测进行客观验证的任务场景。

从整体架构看，项目设计方向可行，核心价值并不只是“用 LLM 生成算子代码”，而是建立一套闭环反馈机制：

```text
任务解析 -> 代码生成 -> 格式转换 -> 自动评测 -> 失败分类 -> Prompt 增强 -> 自动重试 -> 经验沉淀
```

该闭环能够把一次性代码生成任务升级为可观测、可迭代、可复盘的自动化实验系统。若实施得当，系统有机会提升算子生成成功率，降低人工排查成本，并逐步积累跨算子的优化经验。

综合判断如下：

| 评估维度 | 结论 |
| --- | --- |
| 技术方向 | 可行，且与算子自动生成任务特性匹配 |
| 架构设计 | 基本合理，分层清晰 |
| 短期 MVP | 可落地，建议聚焦单轮生成、评测和失败记录 |
| 中期闭环反馈 | 有明显价值，但依赖高质量评测输出和失败样本 |
| 长期知识库与自动优化 | 有潜力，但复杂度较高，需谨慎推进 |
| 最大风险 | 评测链路稳定性、失败归因准确性、性能结果可重复性 |

建议采用渐进式实施策略：先跑通最小闭环，再逐步引入失败分类、自动重试、性能基线、知识库和高级优化能力。

## 2. 项目可行性总体判断

### 2.1 总体结论

项目具备可行性，但不宜一开始追求完整平台化能力。更合理的实施方式是先构建一个极小但稳定的闭环 MVP，确认自动反馈机制确实能够提升生成成功率，再扩展到知识库、性能优化、多生成器融合和 Dashboard 等能力。

推荐将项目定位为：

```text
面向 CANN 算子生成任务的自动化评测闭环系统
```

而不是：

```text
通用 LLM 代码生成平台
```

这种定位更务实，也更容易形成可验证的工程成果。

### 2.2 模块可行性评估

| 模块 | 可行性 | 说明 |
| --- | --- | --- |
| 配置解析 | 高 | YAML 配置加 CLI 覆写属于标准工程能力，实现难度低 |
| 任务队列 | 高 | 可基于 multiprocessing 或任务调度器实现 |
| 设备池管理 | 高 | 独占/共享设备分配机制清晰，早期可用 deque 实现 |
| 状态持久化 | 高 | JSON 或 SQLite 均可满足早期需求 |
| 单轮代码生成 | 中高 | 依赖生成器接口稳定性和 prompt 质量 |
| submission 格式转换 | 中高 | 关键在于目标评测系统的输入格式是否稳定 |
| kernel_eval 调用封装 | 中高 | 工程难度可控，但需要处理环境、超时和日志问题 |
| 失败分类器 | 中高 | 第一版可用规则分类，不必依赖复杂模型 |
| Prompt 增强器 | 中 | 能实现，但效果依赖错误信息质量和压缩策略 |
| 自动重试控制器 | 中 | 策略可控，但需要防止无效重试浪费资源 |
| 性能基线管理 | 中 | 数据结构简单，难点在于性能测量稳定性 |
| Knowledge Base | 中低 | 存储容易，难点是检索、筛选和有效注入 |
| Profile 引导优化 | 中低 | 依赖 profiler 输出结构化程度和可执行优化策略 |
| 多生成器融合 | 中低 | 资源消耗较高，适合作为后期增强 |
| Dashboard | 中 | 技术实现不难，但早期不是核心价值来源 |

## 3. 核心价值分析

### 3.1 从一次性生成升级为闭环系统

传统 LLM 代码生成流程通常是：

```text
输入 prompt -> 生成代码 -> 评测失败 -> 人工查看日志 -> 人工调整 prompt
```

该项目希望将流程升级为：

```text
输入任务 -> 生成代码 -> 自动评测 -> 自动分析失败 -> 自动增强 prompt -> 自动重试 -> 记录经验
```

这使系统从“生成工具”变为“自动化实验与优化系统”。对于 CANN 算子生成而言，这一点非常关键，因为算子实现是否正确、是否高效，都可以通过客观评测获得反馈。

### 3.2 分层架构具备扩展性

设计中将系统拆分为以下层次：

| 层级 | 职责 |
| --- | --- |
| CLI / API 层 | 参数解析、运行控制、监控、重试入口 |
| Orchestrator 编排层 | 任务队列、设备池、并发控制、超时与状态管理 |
| Generator 生成器层 | 接入 AKG、LLM、模板或混合生成方式 |
| Converter 转换层 | 统一产物格式，生成 submission |
| Evaluator 评测层 | 调用 kernel_eval，采集正确性与性能结果 |
| Feedback Loop 反馈层 | 失败分类、归因分析、Prompt 增强、重试策略 |
| Persistence 持久层 | 保存状态、产物、评测结果、基线和知识库 |

这种分层方式合理，能够降低模块耦合，并允许后续替换生成器、评测器或反馈策略。

### 3.3 适合工程化沉淀

CANN 算子生成任务具有以下特点：

- 输入任务结构相对明确，例如 schema、shape、dtype、golden 实现和测试用例。
- 输出结果可以通过编译、运行、精度和性能评测验证。
- 失败类型具有一定重复性，例如 shape 不匹配、dtype 错误、axis 处理错误、CANN API 不支持、性能不足等。
- 同类型算子之间存在可复用经验，例如 reduce、matmul、elementwise、broadcast 等模式。

这些特点使该项目适合引入失败记录、负面示例库、性能基线和 Knowledge Base。

## 4. 主要风险与应对建议

### 4.1 评测链路不稳定

#### 风险说明

项目最大风险不是生成器能否产出代码，而是评测链路是否稳定、可重复、可解释。如果 `kernel_eval` 输出格式不稳定，或者同一 kernel 多次运行性能波动较大，则反馈系统会受到噪声影响。

典型问题包括：

- 同一算子多次运行 latency 波动较大。
- 设备状态、缓存、温度、后台负载影响性能结果。
- 编译失败、运行失败、环境失败混杂在一起。
- profiler 输出不稳定或难以结构化解析。

#### 应对建议

- 先建立稳定的单轮评测链路，再实现复杂反馈机制。
- 对性能数据进行多次采样，推荐使用中位数或 p50/p90，而不是单次 latency。
- 明确区分系统环境错误、编译错误、运行时错误、精度错误和性能错误。
- 保留完整评测输入、输出、stderr、stdout、环境变量和设备信息，方便复盘。

### 4.2 失败分类误判

#### 风险说明

失败分类器如果过度自信，会导致错误的修复方向。例如将运行时崩溃误判为精度错误，可能导致下一轮 prompt 注入错误提示，降低生成质量。

真实失败往往不是单一原因：

- 编译通过但运行结果错误。
- 运行通过但部分 shape 错误。
- 精度错误来自 dtype 截断或 broadcast 逻辑。
- 性能不足来自数据布局、访存、tiling 或同步开销。
- 超时可能来自死循环、编译卡住或设备异常。

#### 应对建议

- 第一版采用保守分类策略，宁可输出 `UNKNOWN`，也不要强行归因。
- 分类结果应包含 `category`、`confidence`、`summary`、`evidence` 和 `suggested_action`。
- 是否重试应由确定性策略控制，LLM 只用于辅助总结和生成 prompt 片段。
- 建立失败样本集，定期评估分类准确率。

### 4.3 Prompt 增强引入噪声

#### 风险说明

如果每次失败都把大量日志、diff、profile 原样塞入 prompt，模型上下文会变得冗余且混乱，反而可能降低下一轮生成质量。

#### 应对建议

- 对 stderr、stdout、diff、profile 进行结构化压缩。
- 每类错误只注入最关键的信息。
- 控制每轮增强内容长度，避免覆盖基础任务描述。
- Prompt 增强应追加结构化 section，不应修改或破坏原始 prompt。
- 每轮 prompt 必须与 `generation_id` 绑定，便于复盘。

推荐的 prompt 增强结构：

```text
[原始任务说明]
...

[前次失败摘要]
category:
confidence:
summary:
evidence:

[修复要求]
1. ...
2. ...
3. ...

[本轮重试约束]
retry_count:
temperature:
generator:
```

### 4.4 Knowledge Base 低效沉淀

#### 风险说明

Knowledge Base 容易变成“存了很多内容但实际不发挥作用”的资料仓库。真正困难的是下一次生成时如何检索、筛选、排序和注入相关经验。

#### 应对建议

- 不要一开始构建复杂 KB，先从结构化失败记录和成功样本开始。
- 经验复用应基于明确命中规则，例如 operator、dtype、shape pattern、failure category、算子模式。
- 每条经验应有权重、适用范围和过期机制。
- 注入 KB 内容前应做排序和去重，避免向 prompt 注入无关内容。

### 4.5 高级优化过早引入

#### 风险说明

多生成器融合、tiling 搜索、profile 引导优化、自动融合探索和 Dashboard 都有价值，但不适合作为早期目标。过早引入会增加系统复杂度，拉长验证周期。

#### 应对建议

- Phase 1 和 Phase 2 聚焦闭环最小可用能力。
- 在闭环成功率提升被证明之前，不建议投入大量资源做 Dashboard 和多生成器融合。
- 搜索式调优应建立在任务去重、评测缓存、基线管理和资源调度稳定之后。

## 5. 推荐实施路线图

### 5.1 Phase 1：最小脚手架

预计周期：2 到 4 周  
目标：跑通单算子单轮生成到评测全过程。

#### 核心功能

| 模块 | 目标 |
| --- | --- |
| 配置解析 | 支持 YAML 任务定义和 CLI 参数覆写 |
| 任务加载 | 能解析算子任务、case、golden 和 schema |
| 生成器接口 | 定义统一 Generator Protocol |
| 产物转换 | 将生成代码转换为 submission 格式 |
| 评测封装 | 能调用 kernel_eval 并保存输出 |
| 状态记录 | 保存每个任务的运行状态和产物路径 |
| 超时控制 | 支持生成、转换和评测阶段超时 |

#### 验收标准

- 给定 1 个算子任务和 1 个 shape，系统能够完整跑完生成、转换和评测。
- 无论成功或失败，都能生成可读的运行记录。
- 失败时能够保留 stdout、stderr、退出码、产物路径和评测配置。
- 任务中断后可通过状态文件判断执行到哪一步。

### 5.2 Phase 2：结构化失败分类与自动重试

预计周期：3 到 5 周  
目标：将失败结果转化为结构化反馈，并驱动自动重试。

#### 核心功能

| 模块 | 目标 |
| --- | --- |
| FailureClassifier | 基于规则识别编译错误、运行时错误、精度错误、性能错误和超时 |
| FailureAnalysis | 输出结构化失败分析 JSON |
| PromptAugmenter | 根据失败类型生成增强 prompt |
| RetryController | 根据类别和重试次数决定是否重试 |
| 重试记录 | 每轮重试都有独立 generation_id |

#### 初始建议

第一版只支持以下失败类型自动重试：

- 编译错误：最多重试 1 次。
- 精度错误：最多重试 2 次。

性能不达标先只记录，不自动优化。原因是性能问题更依赖稳定评测、多次采样和 profile 分析，早期直接自动重试容易消耗大量设备资源。

#### 验收标准

- 能对主要失败类型输出结构化分类。
- 能基于分类结果生成增强 prompt。
- 能完成至少 1 次自动重试。
- 每轮生成、prompt、产物、评测结果和失败分析可追踪。
- 自动重试能带来可观测的成功率提升。

### 5.3 Phase 3：性能基线与知识沉淀

预计周期：4 到 8 周  
目标：建立跨运行的性能基线和可复用经验库。

#### 核心功能

| 模块 | 目标 |
| --- | --- |
| PerfBaseline | 记录每个算子的历史最佳性能 |
| PerfRecord | 保存每次评测的 latency、throughput、shape、dtype 和 generation_id |
| BaselineComparator | 判断性能提升、持平或回归 |
| Knowledge Base | 记录成功策略、失败模式和人工/自动总结经验 |
| Negative Examples | 将高频失败模式转化为负面示例 |

#### 基线更新建议

| 条件 | 动作 |
| --- | --- |
| 新结果优于基线 5% 以上 | 更新基线并保存最佳 kernel |
| 新结果在基线 ±5% 内 | 记录结果但不更新基线 |
| 新结果低于基线 10% 以上 | 标记为性能回归 |

该策略的前提是性能测量波动小于阈值。如果设备环境本身波动达到 5% 到 10%，则需要先扩大采样次数或调整阈值。

#### 验收标准

- 能跨运行保存和查询性能历史。
- 能识别性能回归。
- 能在同类算子的后续生成中注入相关经验。
- Knowledge Base 注入内容能被追踪，并能评估其对成功率的影响。

### 5.4 Phase 4：高级优化与平台化

预计周期：持续迭代  
目标：在前面闭环稳定后，引入更高阶的自动优化能力。

#### 可选能力

| 模块 | 目标 |
| --- | --- |
| 多生成器融合 | 同时尝试 AKG、LLM、模板等生成方式，选择最优结果 |
| 搜索式调优 | 对 tiling、block size、buffer 策略等参数进行搜索 |
| Profile 引导优化 | 解析 profiler 输出并定向生成优化建议 |
| 自动融合探索 | 识别相邻算子并尝试融合 |
| Dashboard | 实时展示任务状态、成功率、性能趋势和失败分布 |

#### 推进条件

建议仅在以下条件满足后启动 Phase 4：

- 单轮评测链路稳定。
- 自动重试已证明有效。
- 性能基线可信。
- 设备资源调度和任务去重机制稳定。
- 已积累足够失败样本和成功样本。

## 6. 关键设计建议

### 6.1 状态存储

早期建议使用 JSON，后续迁移到 SQLite。

| 阶段 | 推荐方案 | 原因 |
| --- | --- | --- |
| Phase 1 | JSON 文件 | 易调试，schema 变化成本低 |
| Phase 2 | JSON 或 SQLite | 视查询需求决定 |
| Phase 3 以后 | SQLite | 支持复杂查询、性能趋势分析和 WAL 并发读取 |

### 6.2 进程隔离

早期建议使用 `multiprocessing`，后期再考虑容器化。

原因如下：

- CANN 环境、驱动、设备映射和权限配置较复杂。
- 容器化会增加早期运维成本。
- 先在宿主机上用进程隔离跑稳，更容易定位问题。

推荐策略：

```text
Phase 1-3：multiprocessing + 进程树追踪 + 超时终止
Phase 4：按需引入 Docker、Sandbox 或更强隔离机制
```

### 6.3 失败分类策略

建议采用“规则分类 + LLM 辅助总结”的混合方式。

| 能力 | 推荐实现 |
| --- | --- |
| 错误类别判断 | 规则引擎 |
| 是否重试 | RetryController 确定性决策 |
| 错误摘要 | 规则提取加 LLM 总结 |
| Prompt 增强内容 | 模板加 LLM 辅助改写 |

分类器输出示例：

```json
{
  "category": "accuracy_mismatch",
  "confidence": 0.82,
  "summary": "输出在 reduce axis=1 的 case 中存在精度不匹配",
  "evidence": [
    "accuracy < 99.5%",
    "max_abs_diff exceeded threshold",
    "failed case: shape=[32, 128]"
  ],
  "suggested_action": "检查 reduce axis、dtype 转换和 golden.py 等价性",
  "should_retry": true,
  "max_retries": 2
}
```

### 6.4 Prompt 增强策略

Prompt 增强应遵循以下原则：

- 保留原始任务说明作为主上下文。
- 失败信息只追加，不覆盖。
- 注入内容必须结构化。
- 日志内容必须截断和压缩。
- 每轮增强 prompt 与 generation_id 绑定。
- 避免把完整 stdout、stderr、profile 和 diff 直接塞进 prompt。

推荐按失败类别分别增强：

| 失败类别 | 注入重点 |
| --- | --- |
| 编译错误 | 编译错误片段、出错文件、行号、API 或语法提示 |
| 运行时崩溃 | crash 类型、调用栈、输入 shape、设备信息 |
| 精度错误 | failed case、max diff、dtype、axis、golden 对照 |
| 性能不达标 | baseline、当前性能、gap、热点算子、profile 摘要 |
| 超时 | 卡住阶段、持续时间、最后日志、资源状态 |

### 6.5 性能评测策略

性能评测应避免单次运行即下结论。

建议：

- 每个 kernel 至少重复运行 5 次。
- 去掉明显异常值。
- 使用中位数作为主要比较指标。
- 同时记录 p50、p90、min、max 和标准差。
- 对性能波动较大的任务增加采样次数。
- 对设备状态、温度、负载和驱动版本进行记录。

### 6.6 产物管理

每次生成都应生成唯一 `generation_id`，并将以下对象绑定：

- 原始任务配置。
- 完整 prompt。
- 生成器类型和模型参数。
- 生成代码。
- 转换后的 submission。
- 编译日志。
- 评测输出。
- 失败分析。
- 重试次数。
- 性能数据。

推荐目录结构：


## 7. 推荐 MVP 范围

第一版 MVP 不应覆盖所有设计点。推荐范围如下：

### 7.1 必须实现

- YAML 任务配置解析。
- 单个算子任务加载。
- 统一生成器接口。
- 单轮代码生成。
- submission 格式转换。
- kernel_eval 调用封装。
- stdout、stderr、exit code 和产物路径保存。
- 任务级状态 JSON。
- 基础超时控制。
- 编译错误和精度错误的规则分类。
- 基于失败分类的一次自动重试。

### 7.2 暂缓实现

- Dashboard。
- 多生成器并行融合。
- 自动 tiling 搜索。
- 自动算子融合。
- 完整 SQLite Knowledge Base。
- Profile 深度优化。
- 容器化沙箱。

### 7.3 MVP 验收目标

MVP 的目标不是追求复杂能力，而是证明闭环有效：

```text
给定一个算子任务，系统能够生成代码、评测失败、识别失败原因、增强 prompt、重新生成，并完整记录每一轮发生了什么。
```

如果该闭环能够在真实任务中提升成功率，就说明项目值得继续投入。

## 8. 建议的核心指标

项目应以效果指标驱动，而不是只检查功能是否完成。

| 指标 | 含义 | 用途 |
| --- | --- | --- |
| single-run success rate | 第一次生成即通过评测的比例 | 衡量基础生成能力 |
| retry success rate | 失败后通过自动重试修复成功的比例 | 衡量闭环反馈价值 |
| classification accuracy | 失败分类准确率 | 衡量反馈分析可靠性 |
| mean time to success | 一个算子从开始到成功的平均耗时 | 衡量整体效率 |
| performance regression rate | 通过正确性但性能低于基线的比例 | 衡量性能稳定性 |
| manual intervention rate | 需要人工介入的任务比例 | 衡量自动化程度 |
| reproducibility | 同一任务重复运行结果是否稳定 | 衡量评测链路可靠性 |
| resource cost per success | 每个成功结果消耗的设备时间和生成成本 | 衡量成本效率 |

建议 Phase 2 重点关注：

- `retry success rate`
- `classification accuracy`
- `manual intervention rate`

如果自动重试能够显著提升成功率，例如将成功率从 40% 提升到 55% 到 65%，则说明闭环反馈机制具备明确价值。

## 9. 决策建议

### 9.1 是否值得启动

建议启动，但应控制第一阶段范围。

推荐理由：

- 项目目标明确，适合工程化闭环。
- CANN 算子生成具备客观评测条件。
- 失败模式具有重复性，适合沉淀经验。
- 分层架构合理，便于渐进式开发。
- 自动重试和失败反馈有机会直接降低人工成本。

### 9.2 启动前应确认的问题

在正式开发前，建议确认以下事项：

| 问题 | 重要性 |
| --- | --- |
| kernel_eval 输入输出格式是否稳定 | 高 |
| 是否已有足够失败日志样本 | 高 |
| CANN 评测环境是否可重复部署 | 高 |
| 是否有稳定可用的设备池 | 高 |
| 现有 auto_pipeline 哪些模块可以复用 | 中高 |
| 生成器接口是否已有约定 | 中高 |
| benchmark case 是否覆盖主要算子模式 | 中 |

### 9.3 推荐技术路线

推荐路线如下：

```text
1. 先复用现有 auto_pipeline 的配置、任务加载、设备池和状态管理思想。
2. 实现最小生成到评测链路。
3. 将所有失败结果结构化保存。
4. 基于真实失败样本实现规则分类器。
5. 只对编译错误和精度错误做自动重试。
6. 证明自动重试能提升成功率后，再做性能基线和 Knowledge Base。
7. 最后再引入 profile 优化、多生成器融合和 Dashboard。
```

## 10. 最终结论

该项目具备明确可行性和工程价值，但成功关键不在于一次性实现完整平台，而在于尽快跑通稳定、可复盘、可量化的最小闭环。

最优先验证的问题是：

```text
自动失败分类和 Prompt 增强是否真的能提升 CANN 算子生成成功率。
```

若 MVP 能证明这一点，则项目值得继续投入，并可逐步扩展至性能基线、知识库、负面示例、多生成器融合和 profile 引导优化等高级能力。

推荐结论：

```text
建议立项，但采用阶段性推进方式。
第一阶段聚焦单算子单轮生成和评测。
第二阶段聚焦失败分类和自动重试。
第三阶段再建设性能基线和 Knowledge Base。
高级优化能力应作为长期演进目标，而不是早期交付目标。
```
