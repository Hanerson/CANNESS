# CANNESS 知识库与 kb_search

## 目录与开发入口

```text
plugin/knowledge_base/
├── entries/
│   └── <id>.md         # 一份文件对应一条可检索的知识
└── *.md                # 现有笔记与旧查询的回退来源
```

插件从配置项 `kbRoot` 指定的目录读取数据。结构化条目放在 `entries/` 的第一层，扩展名为小写 `.md`。每次查询读取磁盘，新增或修改条目在下一次查询生效。检索使用本地词项匹配和元数据过滤，运行时依赖 Node.js 和现有 dsh 工具接口。开发者可以从[填充指南](../guides/knowledge-base-authoring.md)复制模板。

## 条目格式 v1

文件为 UTF-8 Markdown。开头两行独立的 `---` 分隔符之间放一个 JSON 对象，第二个分隔符下方写 Markdown 正文。文件名使用 `<id>.md`。模板与说明放在 `entries/` 外，校验器会把该目录中的每个 Markdown 文件当作正式条目。

必填字段

- `schema_version` 固定为整数 `1`。
- `id` 为稳定的全库 ID，使用小写字母、数字和连字符，最长 80 字符。例如使用 `<op>-<topic>-<target>` 的形式。修改措辞时沿用原 ID。
- `title` 为能直接描述问题或策略的标题，最长 120 字符。
- `kind` 取 `contract`、`implementation`、`troubleshooting` 或 `benchmark`，分别用于接口与语义、实现方案、诊断与修复、性能证据。
- `evidence` 取 `specification`、`source_inspection`、`reported` 或 `reproduced`，分别表示规格明确要求、静态源码观察、材料中的报告、带复测记录的结论。一个条目有一个证据等级，混合等级的结论拆成多条。
- `sources` 为 1–8 个来源对象。每个对象须有 `ref`（最长 500 字符），可以带 `sha256`（64 位十六进制）。来源可以是文档链接、版本化的仓库位置、报告位置或压缩包内定位串。散列对应引用的原始文件，ZIP 引用记录整个 ZIP 的散列。

可选字段

- `operator` 使用规格书里的规范算子名。跨算子通用条目省略此字段。
- `aliases` 记录该算子的其他名称，填写时须同时有 `operator`。只在拼写或语义确实等价时填写，避免把算子变种当作别名。
- `hardware`、`dtypes`、`layouts`、`cann_versions` 限定适用范围。查询会把省略的字段当作没有已声明限制，因而平台专属结论应显式填写平台。版本用具体版本字符串，shape、axis、对齐、尾块和其他组合条件在正文说明。多个字段各自为候选集合，适用条件随硬件和 dtype 组合改变时，拆成独立条目，避免隐含错误的组合。
- `keywords` 放正文未必出现的检索词，如 API 名、常见错误签名、中英术语和硬件瓶颈名。

除有专门说明的字段外，字符串最长 120 字符，可选数组填 1–16 项，省略没有值的字段。正文去掉外围空白后须为 1–1,800 字符。正文应能独立说明适用条件、结论和如何核对。单条序列化后最多 7,900 字符，给结果信封留出空间。字符长度按 JavaScript UTF-16 code unit 计算。

## 查询契约

至少提供 `operator_name` 和 `query` 中的一项。字符串参数不能只包含空白；`query` 最长 500 字符，其他字符串参数最长 120 字符。

- `operator_name` 用于精确匹配规范名或别名。
- `query` 接受中文关键词、英文、API 符号或报错片段。建议保留辨识度较高的诊断词和代码符号。
- `hardware`、`dtype`、`layout`、`cann_version` 匹配条目的对应适用范围。参数各接收一个值。
- `kind` 精确匹配条目类型，允许值同元数据。
- `limit` 必须是 1–8 的整数，默认 4。

```json
{
  "operator_name": "ExampleOp",
  "query": "尾块 TailMask",
  "hardware": "950pr",
  "dtype": "bf16",
  "layout": "strided",
  "kind": "implementation",
  "limit": 3
}
```

只传 `operator_name` 时返回兼容文本。优先展示命中的结构化条目，包含元数据、来源和正文。没有结构化算子命中时，沿用根目录笔记的文件名子串查找和 8,000 字符文本上限；没有匹配文件时返回 `no knowledge entry for <name>`。

其他合法调用返回 `{ "schema_version": 1, "hits": [...], "has_more": false }`。每个命中包含完整的条目元数据和 `body`。命中为空时返回 `hits: []`。当数量上限或序列化预算使部分结果未返回时，`has_more` 为 `true`，可缩小查询范围。整个结构化结果序列化后不超过 8,000 字符，预算按排序后的完整条目分配。缺失来源无法自动打开或核验时，返回条目记录的引用文本即可。

结构化查询只使用 `entries/` 中通过校验的条目。只有根目录旧笔记的知识库可以继续用兼容查询，结构化查询在有相应条目后才会召回。格式错误会报出文件名和出错字段；无效查询与合法的零命中可明确区分。

## 匹配与排序

1. 先应用 `kind` 和算子约束。名称和别名忽略大小写及分隔符；当同时传入 `query` 时，主题匹配的通用条目也可以召回。只传 `query` 时搜索全部算子和通用条目。
2. 过滤与指定硬件、dtype、布局或版本明确冲突的条目。例如 `950pr` 与 `910b` 各自独立，`bf16` 与 `bfloat16` 等价。CANN 版本使用精确匹配。
3. 对中文使用相邻双字词项，对 ASCII 单词、驼峰和带连接符的标识符保留整词及其组成词。标题、名称、别名和关键词每个匹配词项计 3 分，正文每个匹配词项计 1 分。词项零命中时排除。分数相同则依次优先直接匹配算子的条目、匹配更多显式适用条件的条目和 ID 字典序靠前的条目。

检索覆盖三种常见开发动作。生成前查询 `contract` 和 `implementation`。遇到编译或精度问题时用错误签名查询 `troubleshooting`。有性能报告时，带上硬件、dtype 和瓶颈关键词查询 `implementation` 或 `benchmark`。工具返回的适用范围和证据类型供调用方判断如何使用。

## 离线验证

在 `plugin/` 下运行 `npm run kb:validate`，校验器与运行时使用同一个解析器。可传入另一个知识库根目录，如 `npm run kb:validate -- ./my-knowledge-base`。定向测试使用临时目录里的合成条目，覆盖工具注册、兼容查询、筛选、排序、预算和格式错误。运行 `npm test -- tests/knowledge.test.ts` 即可复验。
