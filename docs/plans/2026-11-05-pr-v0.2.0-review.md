# CANNESS 验收意见与修改指导

## 0. 总体结论

| 项 | 评价 |
|---|---|
| 方向 | **正确**。把“假评测”（`watch.py` 直接写目标值）换成真实编译 + msprof，是必须走的一步 |
| 工程质量 | **良好**。TDD 覆盖、文档同步、失败语义都有交代，`REPORT-A.md` 的“偏差说明”也写得很诚实 |
| 可合入性 | **可以合并**，但**不可作为“评测已真实化”发布**，应先补 M1 |

**一句话结论**：这次 PR 完成了“评测器侧”的契约，但**没有完成“产出物侧”的契约**，因此真实闭环仍然跑不通。M1 之前，任何真机 `run_evaluation` 都会返回 `compile_fail`。

问题按严重度分为三档：

- **M1 / 阻断**：真实链路无法跑通，发布前必须修
- **M2 / 重要**：不影响“能不能跑”，但影响“跑得对不对、好不好用”
- **M3 / 收尾**：一致性与卫生问题

下文每一条按 **现状 → 问题（为什么不对）→ 预期设计 → 修改建议 → 验收标准** 展开。

## M1-1 构建契约断层：`build.sh` / `run_once.sh` 无人产出

### 现状

`plugin/remote/runner.py` 的 `evaluate()`：

```python
build = package / 'build.sh'
run_once = package / 'run_once.sh'
if not build.is_file() or not run_once.is_file():
    report = make_report(generation, target, status='compile_fail', summary=CONTRACT_ERROR)
    # CONTRACT_ERROR = 'package does not implement build contract v1'
    return report
```

而生产侧 `plugin/src/package-files.ts`：

```ts
export function buildTestPackage(workspace, generationId, spec) {
  cpSync(src, dest, { recursive: true })            // 只复制四层
  writeFileSync(join(dest, 'manifest.json'), JSON.stringify({ ... }))
  return dest
}
```

`write_operator` 只有 `kernel` / `host` / `api` / `plugin` 四个必填字符串参数，**没有任何工具能往包里写额外文件**。

### 问题（为什么不对）

1. **真实闭环恒失败**。按标准顺序 `submit_spec → write_operator → build_test_package → run_evaluation`，第 4 步必然得到 `compile_fail: package does not implement build contract v1`。
2. **失败会被误记为编译问题**。该 `compile_fail` 计入 `compileRetries`，3 次后 `stopped: compileRetries`，任务直接终止。
3. **单元测试“绿”掩盖了问题**。`eval-runner.test.ts` 自带 fixture 包（`tests/fixtures/eval-contract/`）当合法输入，测的是 runner 而不是“生成器 → runner”这条真实链路，所以测试全绿与链路不通并存。
4. **文档撕裂**。同一次 PR 里 `Remote_NPU_Runner.md` 要求包内有 `build.sh` / `run_once.sh`，而根 README §9 仍写“`build_test_package` 复制四层文件并生成 `manifest.json`，远端拿到即可编译”。两份文档对同一个包给出互相矛盾的定义。

### 预期设计

**插件必须对“包能不能跑起来”负责，但只负责算子无关的部分。**

build 契约里其实是三件事，性质不同，应分属不同所有者：

| 部分 | 性质 | 所有者 |
|---|---|---|
| 编译编排（bisheng 参数、`-lascendcl -lruntime` 链接、exe 产物） | 算子无关，CANN 公共知识 | **插件骨架** |
| 主程序（`aclrtMalloc` → 拷贝 → launch → `SynchronizeDevice` → 精度对比 → 打 `CANNESS_RESULT`） | 流程固定 | **插件骨架** |
| 精度参考 golden | 每个算子一个公式 | **模型 / 知识库** |

结论：`build_test_package` 应在“四层 + manifest”之外，**渲染出构建契约文件**，模板不按算子类型分化，只按输入输出个数泛化。

### 修改建议

1. 新增 `plugin/templates/build-contract/`，含 `build.sh`、`run_once.sh`、`main.cpp`、`golden.h` 四个模板。
2. `build_test_package` 在复制四层之后渲染这四个文件：
   - `build.sh`：编译 kernel + main，链接成 exe，**最后一行 stdout 打印 exe 绝对路径**；
   - `run_once.sh`：跑 1 次 exe，解析 `CANNESS_RESULT`；
   - `main.cpp`：ACL 骨架，按 spec 的 `input_specs` / `output_specs` 个数与 dtype 生成张量分配、填充、拷贝、launch、同步、误差统计；
   - `golden.h`：算子精度参考，首版为占位实现（见 M1-2）。
3. tiling 统一用通用 `CannessTilingData { totalLength, blockLength, tileLength }` 与配套 shim 头，**不再要求每个算子自带 `GeluTilingData` 这类命名**（现在的 `host.cpp` 里 `context->GetTilingData<GeluTilingData>()` 和 kernel 侧 `GET_TILING_DATA` 是算子相关的，约定成通用结构可让模板与算子解耦）。
4. `soc_version` 从 spec 的 `target_platform.soc_version` 推导，缺省 `Ascend910B2`；编译参数（`--cce-soc-core-type=VecCore`、`--cce-soc-version=...`、`-include shim`、`-lascendcl -lruntime`）直接写进模板，不再由模型或使用者决定。
5. `manifest.json` 的 `files` 字段改为**实际落盘清单**（含模板产物），保证“清单 = 包内容”。

### 修改建议（模型可用的最小扩展点）

**不要**把“模型自由写 `build.sh` / `main.cpp`”作为主路径（每个算子重写 90% 重复代码，且必然重复踩 `VecCore`、`AIV-only`、tiling 放 device 这些已经写进知识库的坑）。只开一个最小口子：

- 新增工具 `write_package_file(path, content)`，白名单**仅 `golden.h`**；
- 模板保持通用，`main.cpp` / `build.sh` 里用注释写明“这段通用，确实需要改请先说明理由”；
- 如果后续有算子确实需要改骨架（多 kernel、多流、特殊 launch），**先改模板**，而不是扩大白名单。

### 验收标准

1. `build_test_package` 产物包含：`build.sh`、`run_once.sh`、`main.cpp`、`golden.h`、`manifest.json`、四层文件；`manifest.json.files` 与实际文件一致。
2. 用现有的 Gelu generation（`canness-workspace/gen-741d0f76`）跑真实 `run_evaluation`，**能编译并运行**，不再返回 `package does not implement build contract v1`。
3. 单测覆盖模板渲染结果的关键元素（exe 路径打印、`CANNESS_RESULT` 行）。

## M1-2 占位 golden 必须“显式失败 + 信息完整”

### 现状

若按 M1-1 引入 golden 插槽，需要定义“模型还没填公式时”的行为。`runner.py` 现有判定：

```python
correctness_ok = int(bad_count) == 0 and max_abs_err <= threshold
if not correctness_ok:
    report = make_report(..., status='accuracy_fail',
                         max_relative_error=max_rel_err, summary=(...))
```

### 问题（为什么不对）

1. **若占位实现返回 0 误差**，会被判 `pass`，等于把 mock 时代的“假通过”重新引回来——这是本次 PR 最想消除的东西。
2. **若占位直接报 `error`**，会把“公式没填”和“运行失败”混为一谈，模型不知道该改 `golden.h` 还是排环境。

### 预期设计

占位 golden 属于“公式还没写”，**判 `accuracy_fail`**（与真实精度不达标同一语义），且报告必须带足信息：

| 字段 | 占位时的内容 |
|---|---|
| `status` | `accuracy_fail` |
| `summary` | `golden not implemented: fill golden.h in the package, then re-run build_test_package and run_evaluation` |
| `correctness.ok` | `false` |
| `correctness.maxRelativeError` | `main.cpp` 输出的**原始 `maxRelErr` 数值**（不是 `null`，便于比较） |
| `runRecord.params.golden` | `placeholder`（换成真实实现后为 `custom`） |

### 修改建议

- `main.cpp` 检测到占位 golden 时输出 `badCount: -1`、`total: <元素数>`；
- **不改 `runner.py` 的判定逻辑**：`badCount == 0` 才通过，`-1` 自然落到 `accuracy_fail`，`maxRelErr` 原样透传；
- `runRecord.params` 增加 `golden` 字段，`report.ts` 的 `parseRunRecord` 已能透传 `params`，无需改解析器。

### 验收标准

- 单测断言：占位 golden 的报告为 `accuracy_fail`、`summary` 含 `golden not implemented`、`maxRelativeError` 为数值、`runRecord.params.golden == "placeholder"`。
- 真机验证：未填公式时返回上述报告，而不是 `pass`。

## M2-1 `kernelTimeUs` 的取值口径需要固定

### 现状

`runner.py` 的 `profile_from_csv()` 把所有匹配行的 `Task Duration(us)` 求平均：

```python
mean = sum(durations) / len(durations)
```

优先读 `op_summary`，其次 `op_statistic`，最后其他 CSV。

### 问题（为什么不对）

1. **与文档口径不一致**。`Remote_NPU_Runner.md` 写的是 `msprof ... --application="<exe> 100"`（100 次迭代）+ 读 CSV，而 `op_summary` 是**逐次**一行，100 行求平均是合理的；但 `op_statistic` 是**聚合**行（avg/min/max），一旦命中 `op_statistic` 且同时命中 `op_summary`，分类去重逻辑依赖文件名前缀，可读性差。
2. **测试没有覆盖多行**。`eval-runner.test.ts` 的假 msprof 只写一行 CSV，因此“平均”这个行为事实上没有被测过。
3. **不同 msprof 版本列名可能变化**。`COLUMNS` 已经有别名表，但没有“一个都匹配不上”时的显式报错路径说明。

### 预期设计

- 明确声明：`kernelTimeUs` = **`op_summary` 中该算子全部行的 `Task Duration(us)` 算术平均**，不做加权、不做首行取值；
- 若只有聚合文件（`op_statistic`），取其 `avg` 列；
- 两者都没有 → `status: error`，`sort` 摘要写明找了哪些目录/文件。

### 修改建议

1. 在 `profile_from_csv` 前显式判断文件族，并在返回的 `summary` 里写明来源（`op_summary` 行数 / `op_statistic` avg）。
2. `eval-runner.test.ts` 增加一条**多行 CSV** 用例（如 3 行 10/20/30 → 平均值 20），把“平均”钉死。
3. 在 `Remote_NPU_Runner.md` 的“结果文件”一节写明取值口径。

### 验收标准

- 多行 CSV 单测通过，且报告 `analysis.summary` 能看出参与平均的行数。

## M2-2 CANNLab 隧道的生命周期没有挂到评测流程上

### 现状

- `cannlab/connect.ts` 维护模块级 `openTunnel`，`startHelperKeepalive()` 每 30s 发一次 `/heartbeat` 保温；
- helper 空闲 10 分钟会自行退出；
- 隧道建立后，卡片把 `host=127.0.0.1`、`port=<随机端口>`、`privateKeyPath=<临时私钥>` 写进 `canness-eval` 配置。

### 问题（为什么不对）

1. **`run_evaluation` 不感知隧道状态**。它只把 `127.0.0.1:<port>` 当普通 SSH 端点。隧道断了、helper 被回收、实例重启导致本地端口变化时，用户看到的是 `ssh connect failed`，而不是“隧道已断开，请重新连接”。
2. **连接失败不可区分**。“本地端口没人监听”与“远端 sshd 拒绝”报同一个错，`REPORT-A` 里也承认“尚未用真实隧道跑过一次 `run_evaluation`”。
3. **保温与评测解耦**。评价一次可能跑 30 分钟，远超 helper 10 分钟空闲回收，而心跳只覆盖 `openTunnel` 存活期间。

### 预期设计

`run_evaluation`（或 `canness-remote`）应在连接前做一次**隧道健康检查**：

- 若当前配置的 `host` 是 `127.0.0.1` 且命中 `currentTunnel()`，先确认 helper 的 `/heartbeat` 可达；
- 不可达时返回可读报告：`tunnel is down; reconnect from Settings → CANNESS`，而不是把错误埋在 SSH 层；
- 隧道存活期间**评测期间持续保温**（或在评测开始时续约一次）。

### 修改建议

1. `cannlab/connect.ts` 导出 `tunnelHealth(): Promise<'up' | 'down' | 'none'>`。
2. `eval.ts` 的 `execute()` 在 `resolveAuth` 之后、`connect` 之前调用，`down` 时返回 `status: error` + 明确摘要。
3. 评测开始前调用一次 `startHelperKeepalive` 的等价保温（或在 `runEvaluation` 的 finally 里停止），避免把心跳定时器泄漏到评测之外。

### 验收标准

- 单测：隧道断开时 `run_evaluation` 返回 `error`，`summary` 含 `tunnel`。
- 真机：断网/关实例后，报告指出隧道问题而不是泛化 SSH 错误。

## M2-3 `fetch_remote_file` 的远端路径没有约束

### 现状

```ts
async execute(args) {
  const target = localTargetFor(config.workspace, args.remotePath, args.localPath) // 只校验本地路径
  const body = await withRemoteHost(ctx, connect, cfg, async files => files.readFile(args.remotePath))
  ...
  writeFileSync(target, body)
}
```

### 问题（为什么不对）

1. 本地路径限制在 workspace 内，但**远端路径不做任何限制**，可读任意可读文件；
2. 读到密钥类文件（如 `~/.ssh/id_rsa`）会被写进 workspace，进而进入会话上下文（DSH 的 `Model-visible means logged` 约束下等于“能被模型看到”）；
3. `remotePath` 非绝对路径时行为未定义（`ssh2` 交给远端 shell 解析）。

### 预期设计

- `remotePath` **必须绝对路径**；
- 默认只允许读 `outbox` 之下、以及 `inbox/<generationId>` 之下；
- 越界时返回明确错误，并在工具描述里写明限制。

### 修改建议

1. `eval.ts` 增加 `remoteTargetAllowed(remotePath, outbox, inbox, generationId)`；
2. 工具 `description` 补一句 “reads are limited to the configured outbox and the current generation's inbox”；
3. 单测补 `../../etc/passwd`、`~/.ssh/id_rsa` 被拒绝的用例。

### 验收标准

- 单测：越界路径被拒绝，错误文案可直接读懂。

## M3-2 `manifest.json` 的 `files` 字段语义

### 现状

```json
"files": ["op_kernel/kernel.cpp", "op_host/host.cpp", "op_api/api.cpp", "op_plugin/plugin.py"]
```

固定四项，与实际包内容无关（模板产物加入后会不一致）。

### 问题（为什么不对）

字段名叫 `files` 却不反映实际文件，属于“说了但没做到”。将来 `runner.py` 若依赖它做校验，会误判。

### 预期设计

- `files` = 包内**实际文件清单**（相对路径，排序稳定）；
- 若要区分“四层”与“构建契约”，另加 `layers` 字段，保持向后兼容。

### 修改建议

- `buildTestPackage` 在写完所有文件后 `readdir` 递归收集，写入 `files`；
- `runner.py` 暂不依赖该字段，仅在结果里不做校验。

### 验收标准

- 单测比较 `files` 与实际磁盘文件集合相等。

## M3-3 精度阈值来源要写清楚

### 现状

`runner.py`：

```python
correctness_threshold(manifest, config)  # 读 maxAbsErr / tolerance.maxAbsErr，缺省 DEFAULT_MAX_ABS_ERR = 1e-3
```

### 问题（为什么不对）

- `spec.ts` 没有容差字段，`1e-3` 是硬编码兜底；
- `REPORT-A.md` §4 已把这一点标为“与任务书的两处必要偏差”之一，说明它尚未被决定；
- fp16 / bf16 的合理阈值差异很大（知识库里 `Exp.md` 用 fp16 `2^-10`、bf16 `2^-7`、fp32 `2^-13`），统一 `1e-3` 对 fp32 太松、对 bf16 太紧。

### 预期设计

- **由模板按 dtype 推导**：fp16 `2^-10`、bf16 `2^-7`、fp32 `2^-13`，写入包内 `config.json` 的 `maxAbsErr`；
- `runner.py` 的读取逻辑不变（已有 `config.json` 优先）；
- `spec.ts` **暂不加字段**，等真实需要自定义时再作为可选字段加入。

### 修改建议

- 模板生成 `config.json`；`Remote_NPU_Runner.md` 写明“阈值由包决定，runner 只读不猜”。

### 验收标准

- 包内 `config.json` 含按 dtype 推导的 `maxAbsErr`；单测断言 fp16/bf16/fp32 三档取值。
